# Кандидатогенерация для поиска услуг Авито (Recall@50)

Решение тестового задания: по поисковому запросу отобрать из корпуса (189 212 объявлений) до 50 кандидатов.
Весь код и пояснения — в [`solution.ipynb`](solution.ipynb). Ноутбук выполняется сверху вниз и в конце пишет `answer.csv`.

**Recall@50 на локальной валидации: 0.922** (3000 запросов, устройство валидации — ниже).
Результат на платформе: 0.843 против 0.922 на валидации. Валидация оказалась оптимистичной: в неё по построению попадают только объявления, уже встречавшиеся в train (иначе нет разметки), а в бенчмарке нужные объявления в основном новые — из корпуса в train есть лишь 10%. Поэтому на валидации переоценены сигналы, опирающиеся на историю объявлений (память, популярность). Исправление — исключать из статистик train все строки с валидационными объявлениями и заново подбирать веса.

## Воспроизводимость

Два прогона ноутбука с нуля (включая пересчёт эмбеддингов) дают побайтово одинаковый `answer.csv` (md5 `89016cd4ae64455cad515072531809ef`) — именно этот файл загружен на платформу. Случайность есть только в разбиении на валидацию, она зафиксирована `SEED = 42`.

## Подход

Скорится **весь корпус** — линейная комбинация сигналов:

| сигнал | вес | что даёт |
|---|---|---|
| BM25 по заголовку (стемминг Snowball) | 1 | точные совпадения слов |
| BM25 по описанию | 1.5 | в описании часто есть слова запроса, которых нет в коротком заголовке |
| BM25 фильтров запроса (`search_infm_params_text`) по параметрам объявления | 0.6 | мягкий учёт фильтров «Вид услуги», «Тип услуги» и т. п. |
| косинус эмбеддингов `multilingual-e5-small` | 60 | синонимы и перефразы |
| log P(локация объявления \| локация поиска) из train | 5 | 83% выборов — в той же локации; «зонтичные» локации (Москва+МО, вся Россия) раскладываются на города |
| log P(подкатегория \| запрос): kNN по текстам запросов train | 1 | тематический априор, особенно для коротких запросов |
| «память»: объявления корпуса, выбранные по похожим запросам в train | 10 | небольшой плюс для популярных объявлений |
| log(1 + число отзывов) | 1 | пользователи чаще выбирают объявления с отзывами |

Как рос результат на валидации:

| шаг | Recall@50 |
|---|---|
| BM25 заголовок | 0.31 |
| BM25 заголовок + описание | 0.39 |
| + априор локации | 0.863 |
| + априор подкатегории | 0.899 |
| + фильтры, популярность | 0.909 |
| + e5, память, подбор весов | **0.922** |

## Валидация

Бенчмарк без разметки, поэтому валидацию собрал из train так, чтобы она повторяла бенчмарк:
* только группы-запросы, у которых **все** выбранные объявления лежат в корпусе бенчмарка — Recall@50 считается
  по тому же корпусу, что и на платформе;
* одна группа на текст запроса (в бенчмарке все тексты уникальны);
* в бенчмарке лишь 37% текстов встречались в train → для 63% валидационных текстов из train удаляются **все** строки
  с этим текстом. Первая версия валидации этого не делала (82% «знакомых» текстов) и была бы слишком оптимистичной;
* статистики из train (локации, подкатегории, память) строятся только по оставшейся части — без утечки.

Стандартная ошибка Recall на 3000 запросах ≈ 0.005, поэтому разницы меньше ~0.003 между вариантами считаю шумом.

## Анализ ошибок

* **Локация — главный источник промахов.** ~60% промахов — объявления не из локации поиска. Хуже всего «зонтичные» локации
  (Москва+МО, вся Россия, СПб+ЛО), где самих объявлений нет: Recall там ~0.84 против ~0.94. Пример: «бурение скважины» →
  «Бурение скважин на воду» — текст совпадает идеально, но объявление из другого города проигрывает по априору.
  Что сделал: вместо жёсткого фильтра — мягкий априор $P(loc_{item}\mid loc_{search})$ по train с псевдосчётчиками;
  вес подобран на валидации (жёстче — теряем такие случаи, мягче — топ забивается объявлениями из других городов).
  Пробовал добавить географическую близость по координатам — прироста нет (+0.0003, в пределах шума), не включил.
* **Лексический разрыв** («аренда краскопульта» → «Прокат инструмента», «замена батарейки в ключе» → «Автоключи,
  программирование») — BM25 не видит связи. Частично закрывают e5 и априор подкатегории.
* **Длинные запросы (5+ слов)** — Recall ниже (~0.88): BM25 требует совпадения многих слов, часть из которых — топонимы
  («сантехник метро раменки»). Помогает e5 и то, что BM25 суммирует по словам, а не требует всех.
* **Шум в разметке** — часть «выборов» почти не связана с запросом («торт 3 шоколада» → «Торт Медовик на заказ»,
  «романтическое свидание» → «Семейный отдых с баней»). Такие случаи кандидатогенерация честно ловить не должна.

## Что пробовал и не взял

* **Географическая близость** по координатам (центроид локации поиска → расстояние до объявления): +0.0003 — шум.
* **Жёсткий фильтр по локации** вместо мягкого априора: теряются выборы из соседних городов.
* **Большие веса** популярности / подкатегории: топ забивается популярными объявлениями нужной темы, но не того запроса.

## Что можно улучшить

* Дообучить e5 на парах «запрос → выбранное объявление» из train (contrastive loss с in-batch негативами) —
  самый очевидный резерв, особенно для семантических промахов.
* Второй этап: собрать ~300–500 кандидатов объединением сигналов и обучить на них ранжировщик (CatBoost/LightGBM)
  вместо линейной комбинации с ручным подбором весов.
